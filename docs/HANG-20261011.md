# The host's hang of 2026-10-11 19:53: a ragdoll gone NaN

The host's game stopped answering during a 0.8.6-rc1 soak, right after the churn script's `load f4mpchurn` and the
`coc` that followed it, and never crashed. This note reads the full-memory dump taken while it hung
(`dumps/host-hang-195346.dmp`), says thread by thread what the game was doing, and what the plugin now does about it.
It is a different hang from the texture wait of 2026-10-17 (docs/HANG-20261017.md). No player names or Steam ids
appear here.

The short version: one of the engine's job threads is spinning, for ever, in Havok's constraint setup, in a loop that
brings an angle into [-pi, pi) and runs while the angle differs from itself clamped. The angle is NaN, which differs
from everything, so the loop never ends. The bodies the angle comes from belong to a skeleton lying in the world near
Sanctuary (a moveable static, `SkeletonClothed02.nif`): every one of its bodies' transforms, and its root node's, is NaN
or infinite. The physics step never finishes, the main thread waits for it, and the game stops. Nothing of the plugin
is on any of the threads involved.

## The material

- `host-hang-195346.dmp`: a full-memory dump of `Fallout4.exe` 1.11.240 (base `7ff7d4e20000`), taken at 19:58:05,
  1 h 9 min into the run.
- `Data\F4SE\Plugins\Fallout4.pdb`: community symbols for the engine. Several names below are coarse (a function the
  pdb names after a destructor is not one); each gets its game offset so it can be checked.
- The plugin build was 0.8.6-rc1; its pdb matched the dump.

Read with cdb from the dump, plus the game's code from `Fallout4.exe` on disk.


The function at +156F5C0 sets up a constraint's angular limits. The thread is at +15718E3, inside this loop
(+15718B1 to +157193C):

```
loop:   ...                         a -= 2pi * floor((a + pi) / 2pi), in xmm5
        ...                         xmm0 = clamp(a, -pi, pi)
+1571929 cmpneqss xmm0, xmm5        F3 0F C2 C5 04
         movd eax, xmm0             66 0F 7E C0
         bt eax, 0                  0F BA E0 00
         jb loop                    0F 82 75 FF FF FF
+157193C ...
```

`cmpneqss` is true for a NaN whatever it is compared with, and `x - 2pi * floor(...)` of a NaN is a NaN, so with a NaN
angle the loop runs for ever. The same loop is copied once more in the function (the exit test at +15725F8, the loop
from +1572580); a scan of the whole `.text` for this shape (a `bt eax,0` taken backwards right after a `cmpneq`) finds
only these two.

The two bodies the thread was working on (pointers on its stack) are `hknpBody`s whose transforms are all NaN
(`7fc00000`/`ffc00000` in every rotation and position lane). Each body's user data is its `bhkNPCollisionObject`; from
there to the scene graph:

```
bhkNPCollisionObject -> LeftLowerLegBone01 -> LeftUpperLegBone01 -> TorsoLowerBone01
  -> SkeletonClothed02.nif (the reference's root) -> DynamicNode -> ObjectLODRoot -> shadow scene node -> WorldRoot Node
```

The bone's world position is NaN (its rotation is still numbers); the root's local and world transforms are NaN with
a few infinities. The root's user data is the reference: `000BDD9A`, a placed reference of the moveable static
`0008B214` (a skeleton), at (-75078, 82804, 7288), near Sanctuary. Its place (`data.location`, `data.angle`) is finite.

### Everyone else

The plugin's own threads are all in waits of their own, none in the engine; the texture update is idle (pending 0, its
lock free). The plugin's log for the run was not kept, and its memory holds nothing from the minutes of the hang.

## What it was not, and what this dump cannot tell

- Not the texture wait: no thread is in it, no move was under way.
- Why the skeleton's physics blew up. A skeleton's ragdoll lying on rough ground can be pushed apart by its own
  constraints until its bodies reach infinity, then NaN, after which the next constraint setup hangs. Whether the
  plugin had a hand in it (by moving something into it, for instance) the dump cannot say: nothing the plugin
  does is known to touch a placed skeleton, and no plugin frame is on any stack, but the log of the minutes before is gone.

## The fix (HavokNan.h, HavokGuard.cpp)

1. **The loop ends on a NaN.** At load, each of the two copies of the exit test is checked to be byte for byte the
   1.11.240 code (`HavokNan::SiteMatches`, and `tools/addrcheck.ps1` checks the same bytes against the installed game).
   Its `bt` and `jb` (10 bytes) become a `jmp` to a detour of ours in the F4SE trampoline: the game's own `bt eax,0`
   and, when the angle is out of range, a `ucomiss xmm5,xmm5`. A number goes back to the loop's top as before; a NaN
   is counted (a locked add on a counter in the detour), the loop's working copy of the angle is set to 0, and it
   jumps out to where the loop would have ended. The result the function goes on with (kept in another register) is
   still NaN, as the body is: the engine carries on with a NaN constraint for that step instead of spinning. The
   detour changes nothing for a number (unit tested against a model of the engine's loop, `EngineWrap`, for every
   class of float).
2. **The NaN body is put right.** Once a frame, on the main thread (`HavokGuard::Frame`): every 5 s the loaded
   references' root nodes and places are checked to be finite, and as soon as the detour has counted a NaN (at most
   once a second) every node of every loaded reference's 3D. A reference found bad is disabled and enabled again half
   a second later, the console's way: its 3D and physics are made again from its place. One that goes bad again within
   a minute, or whose place itself is not finite, is disabled and left so. The player and the session's own stand-ins
   and mirrored NPCs are never touched, only logged (`HavokNan::Cleanup`, unit tested).

The log says each step: `Havok NaN: the constraint setup's angle loop ends on a NaN (2 of 2 copies)` at load,
`Havok NaN: N NaN angle(s) cut ...`, then `Havok NaN: <ref> ... has a transform that is not finite: reset (disabled
and enabled again)` and `Havok NaN: <ref> enabled again ...`.

The dev channel's `havoknan` shows the counts, looks on demand, and makes the dump's state on purpose
(docs/DEV-CHANNEL.md).

## The live test (2026-10-18, host and VM joined at SanctuaryExt)

On the skeleton itself: `console player.moveto 000BDD9A`, then `havoknan poison BDD9A dynamic` (17 bodies, all 17
reading back NaN). The host's log:

```
[09:26:21.309] Havok NaN: the constraint setup's angle loop ends on a NaN (2 of 2 copies)
[09:27:19.819] Havok NaN: poison (dev): 17 bod(ies) of 000BDD9A (base 0008B214, type 38) at (-75078, 82804, 7289), node 'SkeletonClothed02.nif' given a NaN rotation (0 static before, all made dynamic, 17 read back NaN)
[09:27:19.820] Havok NaN: 000BDD9A ... has a transform that is not finite: reset (disabled and enabled again)
[09:27:19.828] Havok NaN: 30 NaN angle(s) cut in the constraint setup since the last look (30 in all); looking for the bodies
[09:27:20.498] Havok NaN: 000BDD9A enabled again: its 3D and physics made again from its place
```

Each of the 30 cuts is a pass through the loop's exit test with a NaN angle, where the game as it was would have
jumped back for ever. The count stayed at 30 after the reset, and the game went on answering. Then three rounds of
`churn.sh 3` (21 cell hops between the two games, 3 saves and reloads, the roles swapped each round): both games in
game throughout, no new crash log on either machine (20 before, 20 after), no further cut on either game.

The game's own `bhkNPCollisionObject::SetTransform` turns a NaN rotation down (the body reads back as before), so
`poison` writes the NaN into the bodies' transforms directly; without `dynamic` it was not tried with that write.
