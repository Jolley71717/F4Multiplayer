# The host's hang of 2026-10-17 22:01: what the dump says

The host's game stopped doing game work right after a `coc SanctuaryExt` from the dev channel, drew a loading screen at
~1800 fps for twelve minutes, answered its window, and never crashed. This note reads the minidump taken while it hung
and says, thread by thread, what the game was waiting on; where the plugin stands in it (outside it); what this dump
cannot tell; what to capture next time; and what a fix could look like. No player names or Steam ids appear here.

The short version: the main thread is inside the engine's own message pump, `PositionPlayerJob::Run`, waiting for the
position-player job to finish. That job runs on one of the engine's job threads and is stuck in the engine's *texture
update* code, spinning on "every texture request of this batch is done". The texture streamer thread, the only thread
that ever marks a request done, is idle with nothing queued. So the batch's bookkeeping says requests are still owed and
no thread is going to deliver them. Nothing of ours is on any of those threads; our frame messages are put off inside
the pump by design, and our threads are all waiting on their own things. The most likely reason the count never
completes is an engine race: the per-frame texture walk, which the main thread runs between frames on a time budget, had
added requests to the shared count but not yet handed them to the streamer when the `coc` began; the job inherits that
count, and the only thread that would hand them over is the one now pumping messages for the job.

## The material

- `hang-20261017-221418.dmp`: a minidump (`.dump /mt`: registers, stacks and thread times, no heap and no data
  segments) of `Fallout4.exe` (1.11.240, base `7ff775fb0000`), taken at 22:14:19, thirteen minutes into the hang.
- `hang-20261017-221418.txt`: cdb's `~*kn` of all 105 threads at capture.
- `host-log-20261017-2214.log`: the plugin log. The last game work is `DevCommands: console coc SanctuaryExt` at
  22:01:17.564; the server thread logs `player 2 left` 0.6 s later (the VM restarting) and the main thread never gets
  to say so; from 22:01:35 `Frame watch: no game work has run for N s while the game drew M frame(s): the F4SE task
  has not run ...` once a minute. 26 649 frames in the first 15 s: ~1800 fps, FastLoad's vsync-off loading screen.
- `sym\F4Multiplayer.dll` + `.pdb`: the build that ran (it names itself `rc2 ba46e59` in the log).
- `Data\F4SE\Plugins\Fallout4.pdb` in the game folder: community symbols for the engine. They name most functions
  right, but a few are coarse: what it calls `Main::ShutdownTextureUpdate+0x2e0`, `+0xa00`, `+0xa70` and
  `WinProc+0xa00` are separate functions (each begins after `int 3` padding with its own prologue). Below they get
  descriptive names, with the game offset so they can be checked.

Everything below was read with cdb from the dump, plus the game's code from `Fallout4.exe` on disk (the dump holds no
code). The game was never started.

## Thread by thread

### The main thread (0, id 0x5140): pumping for the position job

```
win32u!NtUserPeekMessage
user32!PeekMessageA
gameoverlayrenderer64!OverlayHookD3D3+0x2a996          the Steam overlay's PeekMessage hook, a pass-through
Fallout4!PositionPlayerJob::Run+0x8b                   +C3B0BB: right after the PeekMessage call at +0x85
Fallout4!Main::OnIdle+0x384                            +C33D54: the frame loop
Fallout4!Main::Run+0xd0
Fallout4!WinMain+0x20
```

`PositionPlayerJob::Run` (+C3B030, 0xEF bytes, as `tools/addrcheck.ps1` reads it) does, in full:

1. `BSJobs::JobList::AddJob(&g_PlayerCharacter+0x28, job = +C3AFF0, &done)` where `done` is a byte on its own stack
   (`[rsp+70h]`, set to 0 first); `BSJobs::JobList::Submit`.
2. `while (!BSJobs::JobList::TryWait(&g_PlayerCharacter+0x28)) { while (PeekMessage(&msg, 0, 0, 0, PM_REMOVE)) {
   TranslateMessage; DispatchMessage; } }`
3. `BSJobs::JobList::Reset`; return the done byte.

The done byte lives at `61b52ff720` on the main thread's stack and reads **0** in the dump. The job list it waits on is
the player's own one-job list; the job is the function at +C3AFF0 (the pdb mislabels it `WinProc+0xa00`): it calls the
position-player worker at +D56330 with `g_PlayerCharacter` and stores the result in the done byte. So the main thread is
waiting for exactly one job, and it is running on thread 60.

`Main::OnIdle` calls the pump at +0x37f only when the "position the player" flag (`+32DD0FB`) is set, which the `coc`
set; the F4SE task and everything else per frame run from this loop, so none of it runs while the pump sits here. That
is why the frame watch reports "the F4SE task has not run": true, and the chain's first link, but not the cause.

The main thread had 4:09 of user and 10:03 of kernel time in the process's 17 minutes: the pump spins flat out on
`PeekMessage` (the other busy threads are the render thread, 73, and an NVIDIA driver thread, 19, drawing the loading
screen at ~1800 fps; that is where the "two cores busy" go).

## The engine's texture update, as far as the code shows it

The blocking wait, the per-frame texture walk and the streamer share one block of globals (the pdb lumps it into
`g_TaskQueueInterface+0x50..`; it is the texture update's own state, at game offset `+32FF858`):

| offset  | what it is                                                                                       |
|---------|--------------------------------------------------------------------------------------------------|
| +0 (50) | active                                                                                           |
| +1 (51) | `pending`: a batch has been handed to the streamer and not yet released                          |
| +4 (54) | `done`: requests finished (or released)                                                          |
| +8 (58) | the second batch (`BSTextureStreamer::TextureModifyBatch*`)                                      |
| +10 (60)| the current batch                                                                                |
| +18 (68)| `total`: requests added to the current batch                                                     |
| +20 (70)| the stage index                                                                                  |
| +60 (b0)| a recursive spin lock: owner thread id at +60, count at +64                                      |
| +78..+8c| the frame's timer start, budget, object counter and "out of time" flag for the per-frame walk    |

The update is a cycle of *stages*, objects in a table at `+2F332E0` whose `Update()` returns true when the stage is
"busy" (stop for this frame) and false when it is finished (go on to the next):

- `TextureUpdateStart::Update` (+C542D0): if `pending && done < total` return busy; else
  `ReleaseBatch(current); done = 0; total = 0; pending = false;` start a fresh batch list, next stage.
- `ProcessObjects::Update` (+C538C0) and its sisters (`ProcessObjectsLOD::Run`, `ProcessObjectsGrass::Run`): walk the
  loaded objects' textures and, for each that should change mip level, `AddToBatch(current, texture, &done, &total,
  level)` (+17C66D0): the request is linked into the batch's list, its `done` pointer stored in it (`request+E0h`),
  its weight set to 1 (`request+114h`), and **`total += 1` at once**. When the batch is full the walk calls
  `SubmitBatch(current)` (+17C67C0: hands the list to the streamer, resets the list, signals the streamer's event)
  and returns busy. The walk is time-budgeted: every 25 objects it compares the frame timer with the budget
  (+C53F07..+C53F3D) and, when over, sets the out-of-time flag and returns 1 from the object loop (+C53F75), so the
  stage reports busy **without submitting**: the requests added so far stay in the batch, counted in `total`, unknown
  to the streamer.
- `TextureUpdateDone::Update` (+C54360): `SubmitBatch(current); pending = true;` back to the start.

Per frame the driver (+C550A0, under the lock, with the frame's budget) runs `stages[index]->Update()` until one
returns busy. Nothing in `Main::OnIdle` calls it directly and no static reference to it exists in the exe, so it is
reached through a pointer set at runtime; it does not matter which, since it is per-frame work and no thread is in it
now.

Requests become `done` only here, and only as `*donePtr = *donePtr + weight` (plain load, add, store):

- `BSTextureStreamer::Manager::ThreadProc+0xae0` and `+0xfee`: the streamer, when a request is finished;
- `ReleaseRequest+0x29` and `ReleaseBatch+0x60`: when a request or a whole batch is dropped (the pdb names
  `ReleaseBatch+0x60` right): every request still in the batch's list is counted and its done pointer cleared, so a
  late finish counts nothing. The streamer's `ReleaseRequest` runs on its thread; `ReleaseBatch` runs on whoever
  resets the batch (the start stage, or the blocking wait).

The blocking wait (+C54910, "wait for this cell's textures") does, with its own stack frame:

1. take the lock; `active = true`; call +C55030: `if (!pending || done >= total) { ReleaseBatch(current); done =
   total = 0; pending = false; }`, `TextureUpdateStage::StartOver`, `ResetAllToggles`, `index = 0`;
2. **again** `if (pending && done < total) skip the reset, else release and zero** (+C54982..+C549BD);
3. swap the second batch in as current (`current = second`, the old current kept in `rsi`) (+C549C4..+C549D2);
4. under the lock, with a budget, run the stages until one returns busy (+C54AE0..+C54AF1); release the lock;
5. `SubmitBatch(current); pending |= true;` (+C54B54..+C54B60);
6. **`while (pending && done < total) { Sleep(0) ten thousand times, then Sleep(1) }`** (+C54B70..+C54BA4): no
   timeout, no second condition;
7. `ReleaseBatch(current); done = total = 0; pending = false;` put the old current batch back (+C54BA6..+C54BE2).

Thread 60 is at step 6, holding the texture update's lock: it is taken at step 1 (+C5491C) and released only after
step 7 (+C54BC9); the two inner takings at +C549DE and +C54A16 are released before step 5. Nothing else waits on that
lock, though (the per-frame driver and the wait both try it once and give up), so it is still a flag wait. (Corrected
on fix/4gb-3: this said the lock was not held.)

## Why it never ends

For step 6 to end, `done` must reach `total` or `pending` must clear. `pending` is cleared only by the resets above,
all of which run on the main thread's per-frame driver or in this very function after the loop. `done` is advanced
only by the streamer thread finishing requests it was handed, or by a release. The streamer has finished everything it
was handed (it is idle on its event with an empty queue) and the count still says requests are owed.

`total` counts every request added to *any* batch since the last reset, and the reset is skipped (step 2) when the
batch the main thread left behind was still pending. The per-frame walk adds to `total` the moment it links a request
into the batch, but the streamer sees that request only at the next `SubmitBatch`, which the walk does when the batch
fills or at the Done stage. A frame in which the walk ran out of budget mid-way leaves requests in the batch that are
counted and not submitted. If the `coc` lands then (`Main::OnIdle` reads the position flag whenever it comes round;
a door or fast travel sets the same flag), the job inherits a `total` that includes them, submits only its own batch, and waits for a
count that only the main thread's next stage walk could complete; the main thread is in `PositionPlayerJob::Run`
waiting for the job. Neither side holds a lock; each waits on a flag the other would set.

That matches every fact in the dump: the done byte is 0, the job is in the Sleep(1) phase of the wait, the streamer is
idle, the main thread pumps, every other thread is at rest, nothing of ours is anywhere near. It also fits the three
occurrences so far: each came right after heavy texture work (a restart's title screen, a cycle of the churn that
spawns a stand-in with a built face and gear and moves the player every minute), when the per-frame walk has the most
to do and is most likely to be cut off by its budget.

What the dump cannot show is the counters themselves: `.dump /mt` keeps no data segments, so `pending`, `done`,
`total` and the batch pointers are unreadable (cdb shows `????????`), and the heap with the batches' lists is gone
too. The chain above is read from the code and the thread states; the "unsubmitted requests" step is the one
inference in it. Two other ways to the same end would look identical in this dump and should stay on the list until
the counters are logged: a request released by the streamer on a path that does not count it (none was found in the
functions read: every release path adds the weight), and the non-atomic `+=` on `done` losing an update (only the
streamer thread writes it while the job waits, so there is no second writer to race it).

## Where the plugin stands

- **Not in the chain.** No engine thread is inside `F4Multiplayer.dll`; our five threads wait on a dev command's
  future, two sleeps and two sockets. Nothing of ours holds anything the job or the streamer needs: the texture update
  uses its own lock and its own flags, and we never touch either.
- **The frame message is handled as designed.** Inside the pump our window procedure defers a frame message
  (`NestedPump`: the pump is on the stack); the watch's once-a-second re-post is dispatched by the pump and deferred
  again. The Steam overlay's `PeekMessage` hook is a pass-through on the stack (it calls `user32!PeekMessageA`
  directly and returns into the pump); it neither eats nor delays messages. Whether the window procedure ran at all
  during the hang (`dispatchedAt`, `lastOutcome`, `framePosted`, `postedAt`) cannot be read from this dump for the same
  reason as the engine's counters; the log's "the F4SE task has not run" is the watch's first stop on the chain and
  says nothing about the messages. Running a frame inside the pump would not have helped and could have hurt; deferring
  is right.
- **Not SaveGuard, not a stand-in's unloading.** The persistence answer is a vtable hook on the stand-in's actor class
  that returns "no" to a question asked on the main thread inside the frame; it is not on any stack, and the position
  worker is past the cell attach when it hangs. A stand-in with a freshly built face adds textures to the walk's work
  like any new NPC does, which makes the window a little wider, no more.
- **FastLoad** (vsync off while the loading menu is up) is why the game drew ~1800 fps while hung, and why the main,
  render and driver threads burn three cores. It does not run before the `coc`, so it does not shape the race window;
  it only makes the hang conspicuous. Capping the loading-screen frame rate would change nothing about the wait.
- **The dev channel's `coc`** goes through the game's console like a typed one: it sets the position flag that
  `Main::OnIdle` reads after the per-frame systems; a door or fast travel sets the same flag. The churn's cadence (a
  `coc` every minute, right after a cycle of spawning and dressing a stand-in) is what makes the rc soak hit this
  engine race more often than play does. The `player 2 left` 0.6 s after the `coc` is the VM restarting on schedule;
  the main thread was already in the pump and never processed the leave; it is a bystander.

## Answers to the four questions

1. **What the position job waits on, and who runs it.** `BSJobs::JobList::TryWait` on the player's one-job list
   (`g_PlayerCharacter+0x28`); the job's result byte on the main thread's stack is 0. The job runs on job thread 60,
   inside the position-player worker, inside the texture update's blocking wait, spinning on `pending && done <
   total`. The fifteen other job threads are idle in their semaphore wait; the texture streamer is idle on its event;
   no engine thread waits on a lock or an event that another holds.
2. **Any thread in our DLL besides our own idle ones?** No. Ours: DevChannel (1) waiting on a command's future,
   HangWatch (97) and the frame watch (98) sleeping, the server (101) and client (102) threads in `select`. No engine
   thread is in a hook or callback of ours.
3. **The overlay's PeekMessage hook; our window-procedure state.** The hook forwards straight to `PeekMessageA` and
   returns into `PositionPlayerJob::Run`; it is not eating or deferring anything. Our globals (`postedAt`,
   `dispatchedAt`, `framePosted`, `lastOutcome`, `inFrame`) are at `F4Multiplayer+0x22F6E3..+0x22F748` but a `/mt`
   minidump holds no data segments, so they are unreadable here. By the code, every frame message dispatched in the
   pump ended as `kDeferred`.
4. **Root cause and fix.** Above and below.

## Read again: how `pending` comes to be set with requests not handed over (fix/4gb-3)

The chain above needs `pending` set while the main thread's batch holds requests counted and not handed to the
streamer. Read as first written, that could not happen: the start stage clears `pending` when it starts a cycle, the
Done stage sets it only after handing everything over, and with `pending` clear the wait's first step (+C55030)
releases the main thread's batch itself (ReleaseBatch counts every request still in it as done) and zeroes the counters,
so a walk cut off by its budget mid-cycle leaves nothing to wait for. What makes it happen is the walk's other hand-over:

- `AddToBatch` (+17C66D0) takes its request from the batch's pool (the batch's vtable slot 1, `[rcx] + 8`); with the
  pool empty it adds nothing and returns false.
- The per-texture walks then hand the batch over and **set `pending`** (+C53ADD: `mov rcx,[current]; call SubmitBatch;
  or [pending],al`, and the same at +C53C98 in the walk over the list of every texture, +C53B40), and return "stop
  for this frame".
- The stage index stays where it is, so the next frame's walk carries on from there, adding to the same batch, now with
  `pending` set: from then until the pool runs out again or the Done stage comes, every request it adds is counted into
  `total` and sits in the main thread's batch. A move that starts in such a frame finds `pending && done < total` at
  +C55030 and skips the reset; the wait sets the main thread's batch aside (in `rsi`), hands over its own, empty one,
  and waits for requests that are in the batch it set aside.

The pool running out is the heavy texture work the three occurrences followed. So the one inference left in the chain
is now a reading of the code too; the live test below shows that state hanging a move exactly as in the dump, and the
hand-over before a move preventing it. (The batch the wait sets aside is the main thread's own, a static object at
+32FF8E8, id 2698368, with a vtable of its own; the second batch is on the heap.)

## The live test (fix/4gb-3, 2026-10-18, the host's game)

`texwait strand` leaves that state on purpose (one real request, for a real texture at the level it is at, counted
into the main thread's batch with `AddToBatch` and not handed over, `pending` set) and runs a `coc` right after.

- **With the hand-over off, the move hangs as on 2026-10-17.** 01:15: strand at `pending=1 done=704 total=1039`
  (stage 0), `coc RedRocketExt`. The main thread entered the pump 82 ms later and nothing walked the textures in
  between (the stage and the batch unchanged); 4.2 s later a job thread took the texture update's lock and the main
  thread's batch was set aside. Then `Frame watch: no game work has run for 15 s while the game drew 29306 frame(s)
  ... the main thread is in the engine's pump, moving the player; the texture wait: pending=1 done=1038 total=1039 (its
  loop goes on), the lock held by thread 0x51fc (count 1), in the wait`: one short, the stranded request. The full dump
  (`hangcatch.ps1 -Now`) has the main thread at +C3B0BB in the pump under +C33D54 in OnIdle, the lock's owner at
  +C54BA4 in the wait's Sleep loop, current = second (the wait's own batch, empty), and the main thread's batch at
  +32FF8E8 with exactly one request in its list. `texwait unstick` (pending cleared): `Frame watch: game work runs
  again, after 252 s`, the player at Red Rocket.
- **A hand-over when the console command is given is not enough.** The first version handed the batch over before
  `console coc`. The move does not start in that call: Main::OnIdle calls PositionPlayerJob::Run 55 to 100 ms (some
  frames) later, and the walk runs in those frames. With the hand-over off, a strand at stage 1 (`pending` clear before
  it, 314 owed, the walk mid-cycle) did not hang (the walk went on to its Done stage and handed everything over); a
  second one at stage 1 did: 274 requests owed at the command, 312 at the call 57 ms later (38 counted in between), and the
  hang with `pending=1 done=0 total=312`, the frame watch adding `the main thread's batch, set aside by the wait, holds
  312 request(s) never handed to the streamer`, and hangcatch printing the same counters before its dump.
- **With the hand-over at OnIdle's call to the pump, no move hangs.** Ten strands with `coc` (two cells in turn), one
  of them at stage 1: ten moves done, each with `Texture wait: before the move, handed the streamer the N request(s)
  the texture walk had counted and not handed over` (N = 165 for the stage-1 one, 1 for the rest), `texwait` showing
  `handed-over-before=10`, and no `Frame watch` stop. Ten plain `coc`s after them: none needed it (the state is rare
  on its own: a 5 s sample at rest found `pending with requests owed` in 0 of 2689 reads). The lock was never found
  held at the call.

## A fix, in two tiers

Tier 1 is in fix/4gb-3 (`TextureWait::Install`, TextureFlush.h), moved from where it was first planned (see the live
test); tier 2 is not, and is only for if tier 1 turns out not to be enough.

**Tier 1, flush right before every move (main thread, low risk).** Main::OnIdle's call to PositionPlayerJob::Run (at
+0x37F, after its test of the position flag) goes through the plugin first: when `pending` is set and the main
thread's batch holds requests, it calls the engine's `SubmitBatch(current)` (id 2275477 with the batch at id 2698351),
under the texture update's lock, so no request is counted and unsubmitted when the job starts. It is what the Done
stage does, on the thread that owns the batch, between frames; from that call until the job is done the main thread
only pumps, so nothing is counted again before the wait. It covers every move: the console's and the dev channel's,
the party's teleport, doors and fast travel. The call is patched only when its five bytes are that call
(`TextureFlush::CallTarget`; `tools/addrcheck.ps1` checks the flag test before it too). First planned before
`DevCommands` hands a `coc` to the console, which leaves the frames before the move starts open.

**Tier 2, unstick from the watch (any move, writes a flag from another thread).** When the frame watch has seen the
main thread inside `PositionPlayerJob::Run` for, say, 30 s (a cell change's texture wait is milliseconds to a couple
of seconds), and `pending` is set with `done < total`, clear `pending` (store 0 at id 2698346) once and log it loudly
with the three counters. The wait loop ends; the job releases its batch (a release counts and detaches every request
still in it, so a late finish by the streamer counts nothing), zeroes the counters, puts the main thread's batch back
and returns; the main thread leaves the pump, and its next stage walk submits the requests that were left behind,
which then complete against a `total` of 0: harmless. This is the same reset the engine's start stage performs on a
batch it gives up on; the only novelty is the thread doing it. The streamer thread is not consulted (whether it is idle
cannot be told cheaply from inside the game); the 30 s limit stands in for that, and a texture wait that genuinely
needed longer would be cut short with its textures streaming in late, which the engine tolerates by design.

Either tier needs the live checks a release candidate gets anyway: a session of doors, fast travel, `coc` from the
console and from the dev channel, with and without a friend's stand-in in the cell, and no `Frame watch` line.
